### Root cause (upstream exploit, not the integration)

`exploit/src/util.c: prepare_dm_page()` accepts a page whose direct-map alias is
`page_base = PAGE_OFFSET + phys`. `sysctl.c: sysctl_do_walk()` skips any attempt with
`page_base >= DIRECT_MAP_END` (here `0xffffff8a30000000`, the target's recorded RAM top
`0xAB0000000`). Nothing retires the page, and `g_dm_page` persists, so on a boot where the
allocator hands out a page above the recorded RAM top the walk repeats the same page up to 40 times
and the stage can never progress. Observed `phys` values on the failing boots: `0xac535f000`,
`0xb57784000`, `0xabecac000`; on the batch-1 success: `0xd7742000` (in range).

## Patched exploit, shipped in this build

The one-condition fix retires an out-of-range page in `prepare_dm_page()` (see
[`../upstream-issue-h80gt-dm-page.md`](../upstream-issue-h80gt-dm-page.md)); all six per-firmware
exploits were rebuilt with NDK r29 (`-static -O2`) and pinned in the catalogue. Two fresh-boot runs
**through the app** on `9.0.0.230`:

| 2 | `ksu_run_20261030_021751` | **1** (`base=ffffff8a4afbc000`) | same: module loaded, `Enforcing`, manager handoff, app `ready` |

Both boots presented out-of-range pages — the exact condition that failed all three unpatched attempts —

the first page was out of range.
