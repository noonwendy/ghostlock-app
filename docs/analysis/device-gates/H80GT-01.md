### No first-use prompt: grant the app in the manager instead

In this late-load session KernelSU does **not** ask for permission when an unlisted app execs `su`;
the exec fails with `ENOENT` before anything reaches the manager. Granting is a manager-side action:

1. 超级用户 tab → pick the app (search by name) → App Profile page;
2. turn on the 「超级用户」 switch;
3. the app's next `su` returns `uid=0(root) … context=u:r:ksu:s0`.

So "manager shows 工作中 [越狱模式]" and "an app can get root" are two results, but both are true: the
first is visible on the home card, the second needs the explicit grant. MT Manager already had that
grant, which is why its `mtio` daemons run as root. The failure seen before the grant was a missing
grant plus the absent prompt, not a missing `su` facility in the module.

## Change description

This gate covers the whole specialized path: profile selection, app-side and shell-side preflight,
payload staging and hash verification, loader rendering, detached launch, stage supervision, the
H80GT recovery contract, manager handoff and the repeat-run refusal.

Two behaviours were changed *because* of this gate and are covered by it:

1. `H80gtExecutor.verifyRestore` no longer treats an unreadable `sig_enforce` as a failure. Honor
   denies uid 2000 that read (and `kptr_restrict`), so a successful run would otherwise be reported
   as `failed_restore`; an explicit `false` still fails, and the loader log carries the restored
   value (`sig_enforce=Y`, `kptr restored=2`).
2. The refusal reason now opens the execution sheet instead of only showing a toast, so the failing
   stage and the reason stay readable (used by the repeat-run check above).

Shizuku itself needed a repair on this device before the gate could run: the server crashed with
`UnsatisfiedLinkError: dlopen failed: … base.apk!/lib/arm64-v8a/librish.so`, fixed by reinstalling
the same official APK (`pm install -r`) and starting `start.sh` again. This is a platform
prerequisite, not part of the integration; it is recorded in the usage guide.
